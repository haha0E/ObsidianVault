# 半结构化数据存储

**一句话**：动态表单、字段经常变的业务，在关系库里常见三条路——JSON 列（PG 首选 jsonb：GIN 索引 + 丰富操作符）、EAV（一行一属性）、宽表不停加字段；权衡点是查询/索引能力 vs schema 演进的维护成本。

## 骨架问题（带着问题学）

- `json` 与 `jsonb` 的本质区别（精确保存文本 vs 分解的二进制）？为什么官方建议大多数应用用 jsonb（处理快、GIN 可索引；代价是写入略慢、丢键序和重复键）？
- jsonb 的两种 GIN 操作符类 `jsonb_ops` 与 `jsonb_path_ops` 差在哪（支持操作符范围 vs 索引更小搜索更快）？
- 动态表单（一个表单几十个组件）落库：JSON 列 / EAV / 宽表加字段，各自的查询、索引、统计、演进成本怎么比？"字段不停新增"为什么会让宽表方案失控？
- MySQL 的 JSON 类型与 PG jsonb 的实际差距在哪（索引方式、操作符与函数生态）？"MySQL 用 JSON 就是找不自在"是不是夸张？
- 反模式信号有哪些：JSON 字段开始参与 JOIN、聚合、高频过滤时，是否该升级成真实列/表？混合方案（核心字段建列 + 长尾字段进 JSON）怎么划线？
